什么是软件保护工程？

软件保护工程，是根据软件资产、威胁模型和部署方式选择防护措施，再用测试证据检查它们带来的变化。它不等于把每个功能都混淆一遍，也不承诺让软件永远无法被分析。

一个实际问题：为什么桌面应用里的核心算法会被恢复？因为程序交付到用户设备后，二进制、符号、常量、控制流和运行行为都可能成为分析线索。保护设计应该从这些暴露面出发，而不是从某种工具的名字出发。
没有 PEA · 你自己逐项调查
  1. 确认核心资产在哪些模块里，以及是否必须随客户端发布。
  2. 分别搜索混淆器、虚拟化方案或编译器功能，手工核验许可证和兼容性。
  3. 自己设计回归测试，判断保护后的行为、性能和包体积是否变化。

需要人工整理的线索

Symbols发布产物是否留下可读符号？
Constants敏感字符串或配置是否直接嵌入？
Trust boundary关键决策是否完全依赖客户端？

示例 prompt · C++ 核心算法
“请评估我自己的 C++ 桌面应用中，哪些信息可能从发布二进制中恢复。比较服务端迁移、符号裁剪、混淆和受限虚拟化，说明许可证、兼容性、性能代价和如何验证。先计划，不要改文件。”

PEA 规划结果应回答

暴露面哪些资产在客户端，哪些风险只是推测。
方案理由为什么优先考虑某项措施，以及放弃了什么。
验证证据需要哪些回归、差分、性能和产物检查。

页面内的流程与结果为教学设计；可下载的原型会对授权目录做真实的只读扫描（证据入库、未知项显式记录），但不执行目标程序，也没有把示例发现伪装成你的扫描结果。

PEA 如何帮助你

把一个模糊的“帮我加固软件”请求，转成可以复核的工程任务。

01界定目标资产、平台、威胁、预算
02研究方案来源、许可、维护、证据
03提交计划适用边界、代价、审批
04验证变化正确性、性能、产物、限制

PEA 的价值不在于列出最多工具，而在于把“为什么选它、改动什么、怎么知道有效、哪里还不确定”放在同一个决策过程里。

从本地目录开始：先看候选项，再生成一份不执行代码转换的规划结果，最后跑通整条证据流水线。

先下载可运行的离线原型：其中包含八个只读分析域、规划器、任务简报与战场反馈回路、证据账本、MCP 工具合同、示例请求与设计文档。解压后，在项目根目录运行下面的命令。

下载 PEA Design Kit v0.5.0 ↓

步骤 1 · 查看本地方案目录
python -m pea.cli catalog
步骤 2 · 按目标与保护意图搜索
python -m pea.cli search --target javascript --goal obfuscation
步骤 3 · 生成计划

预期结果：步骤 1–3 产出带候选方案、理由和限制的本地 JSON 计划；步骤 4 产出一份脱敏 Markdown 报告与可复现的 JSON 证据包——侦察与各域观察进入证据账本，未消解的阻塞项让 verified 门禁保持关闭。它不会替你安装保护器，也不能证明某个二进制已得到保护。

上述命令需要 PEA-Design-Kit 项目文件。请先从项目设计包解压，再在项目根目录运行；它不依赖第三方 Python 包。

常见问题

PEA 是 REA 的官方分支或合作项目吗？

不是。PEA 是独立项目，借用“逆向工程 / 保护工程”这组方向对照来解释自己的定位；它与 REA 没有官方隶属或合作关系。REA 的来源请参见 REA 官网。

PEA 已经能自动保护任意程序了吗？

还不能。当前原型提供：八个只读分析域（对授权目录做真实扫描，结论带覆盖范围与未知项）、暴露面分层、保护计划生成、任务简报与攻击自测设计、证据账本与 verified 门禁、战场反馈回路（破解包 diff 入账 + 服务端响应计划）、任务编排与断点恢复（`pea task` / `pea.run_assessment`，任务落盘、输入摘要恢复、失败域不假绿灯），以及 35 个 MCP 工具合同（35 个全部已接线、带审批强制）与标准 MCP stdio server（`pea mcp-server`，官方 SDK 可选依赖，协议层零豁免）。受控执行闭环已落地（0.7.0）：`pea protect <项目路径>` 一条命令完成分析 → 方案 → 审批预览 → 唯一人工决策（y/N）→ 在 PEA 受管工作区内执行已审阅的变换 → 独立验证（含变换有效性门：产物没变即判失败，工具退出码 0 不算证据）→ 前后差分 → 报告；配套的 JS 样板七步闭环与八条判据已机械核验。尚未提供：在线研究连接器、真正的 IR/VMP 后端、宿主确认界面，以及 Flutter / R8 / native 多平台执行。

使用混淆或虚拟化，就能阻止逆向吗？

不能。它们通常只能提高分析成本。对高价值秘密，应优先考虑能否移到可信服务端；对必须在客户端运行的逻辑，则需要明确攻击假设，并通过可复核测试说明保护措施的实际影响。

PEA 会不会未经同意修改项目或运行外部工具？

设计原则是默认只读：分析域只读，且从不执行你的项目代码。执行只发生在 PEA 受管工作区（目标项目的一份快照）内，用户工程目录只读不写。真正执行需要串起几道显式门：先给出精确预览（工具与版本、受影响文件、预期副作用），再由人确认（pea protect 的 y/N 或独立的 pea approve——模型的自述授权不算审批），最后用一次性令牌绑定工具版本与计划 digest 才能执行；执行授权根由运营者环境配置，未配置则执行面整体关闭。

参与软件保护工程

PEA 的方向是把保护研究、方案选择、集成审批和验证证据放进同一条工程工作流。你可以从设计规格、MVP backlog 和离线原型开始了解项目，再决定从哪一层贡献。

PEA · Protection Engineering Assistant

独立开源方向。视觉和叙事上与逆向分析工作流形成对照，但不代表与 REA 存在官方关系。当前网页展示的是设计与原型状态，不应把拟议功能误认成已经发布的能力。
