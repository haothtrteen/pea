# `lang-vmp-guide` 在 PEA 中的接入评审

**评审日期：** 2026-10-13 · **评审时点 PEA 版本：** 0.2.2  
**用途：** 将用户提供的跨语言 VMP Skill 纳入 PEA 的研发工作流，并区分可迁移的方法、平台专用假设和待验证主张。

## 1. 结论

此 Skill 的价值主要是工程方法论：在变换前明确攻击面、选择解释器插桩点、维护唯一保护目标清单、逐个函数进行保护与差分验证，并把保护边界写进 threat model。它适合作为 `pea-vmp-research` 的知识源，而不适合当作一份在所有平台都可直接执行的脚本。

原始压缩包未携带单独 LICENSE 文件。PEA 可以在内部将它作为用户提供的参考材料；公开仓库发布原包或其衍生内容前，应由权利人明确授权范围和许可证。PEA 自己撰写的总结文本应使用独立许可证，不能自动替原 Skill 声明许可。现在已找到公开的 [ShellVMP](https://github.com/haothtrteen/ShellVMP) 与 [FDartVMP](https://github.com/haothtrteen/FDartVMP) 官方仓库，并核对其公开 README/许可说明；这不等于已经 clone、固定 commit 或源码级复核。


## 2. 关联项目的公开资料核对（不是源代码审计）

- **ShellVMP**：官方仓库描述 V6 脚本混淆、V7 ELF 封装/流式解密和 V7-ISA 解释器令牌化 PoC，并提供预检、集成测试和目标函数定位工具。页面列出 AGPL-3.0 及商业许可文件。对 PEA 的可迁移价值主要是目标清单、变换前兼容性检查、构建后差分和错误路径记录；不能把项目 README 对抗调试/反内存读取的声明当成普遍保证。
- **FDartVMP**：官方 README 描述 Dart 函数到自定义指令/原生解释器的路径，并声明了编译、运行、差分与 APK 检查闭环。`LICENSING.md` 说明 AGPL-3.0-or-later 与商业双授权。其“Honest limitations”明确指出解释器可以被分析、Dart 调试器能观察堆和返回值、运行时派生逻辑仍存在；文档也说明 VMPacker 是单独工具/许可。
- **核验等级**：以上为 `documentation_reviewed`。评审时点容器无法解析 `github.com`（该限制后来已解除，REA 源码已取得；但 ShellVMP / FDartVMP 本文档仍未拉取源码，等级不放行），因此代码路径、真实测试可复现性、精确 commit、完整第三方依赖和目标项目兼容性均标记 `unknown`。PEA 不会把这些项目默认作为依赖，也不会复制其实现。

## 3. 可迁移的工程经验

| Skill 中的原则 | PEA 中的落点 | 验证门槛 |
|---|---|---|
| 按攻击路径分工，不为堆层数而堆层数 | Exposure Mapper + Strategy Engine | 每个控制对应一个资产/风险、证据和残余风险 |
| 同时评估结构与词法泄露 | 发布工件扫描 + 程序结构/调用关系评估 | 报告覆盖范围、能观察到的锚点和未知区域 |
| 插桩点必须实际命中 | adapter fixture、构建探针/覆盖率（仅测试版本） | 必须有测试证明变换路径被执行，不接受静默跳过 |
| 保护目标清单有单一真源 | `protection_manifest.json` / function allowlist | 保护目标不存在、发生漂移或被优化删除时应显式失败 |
| 翻译成功不等于语义正确 | 差分测试、边界测试、随机测试 | 返回值/副作用/退出码/异常均要对比 |
| 记录构建过程和输入输出摘要 | Evidence Ledger、artifact manifest、tool lock | 同一固定配置能重现或解释差异 |
| 先逐函数验证再批量扩展 | 从一个函数到一个模块的阶段门 | 新增范围前保留基线与回滚点 |

## 4. 需要降级为假设的内容

| 主张/机制类别 | 为什么不可直接推广 | PEA 如何处理 |
|---|---|---|
| Linux `seccomp`、`TracerPid`、`PR_SET_DUMPABLE` | 依赖 Linux 内核、权限、系统调用路径和部署约束；无法覆盖所有读取/调试方式 | 作为平台特定 control；测试所支持的内核/架构，不宣称“唯一确定性手段” |
| root 下的“信噪比稀释” | 其效果取决于数据布局、攻击者观察能力和分析任务；不构成密码学保证 | 只可作为研究假设，不能进入安全承诺或默认实现 |
| “检测入侵就毒化密钥” | 会让行为难以诊断，可能造成数据损坏或可用性问题 | 默认 fail-closed + 明确错误；服务端密钥吊销须经过受控、可审计的业务流程 |
| “磁盘永无明文” | 临时文件、swap、日志、core dump、缓存、打包脚本都可能泄露；运行时一定存在解释执行所需语义 | 定义精确工件范围，进行磁盘、临时目录、日志和崩溃工件扫描，并说明运行时窗口 |
| Bash 主执行分派点、解释器 hook | 取决于具体解释器实现和版本；并非所有语言存在统一的调用分派点 | 每个语言独立建立语法/词法/运行时调用图和探针 fixture |
| GPR-only/NEON、ELF 尾载荷与自修改细节 | 依赖 CPU ABI、编译器、链接器与工具链行为 | 纳入目标架构兼容矩阵；没有实测时禁止自动应用 |
| 通过加密/令牌化达到“不可恢复” | 解释器运行时需要恢复或消费语义，攻击者可能观察运行时行为 | 用“提高静态分析成本”表述，结合服务端边界与回归验证 |

## 5. PEA 专用 Skill 的建议接口

输入：

- 目标语言、解释器和精确版本；
- 用户确认的源码/工件范围与授权；
- 是否必须离线执行；
- 需要保护的函数或脚本模块；
- 当前构建系统、架构、平台和测试入口；
- 性能、包体积、启动时间、兼容性预算；
- 用户允许的依赖许可证和网络源。

输出：

- 可迁移方法列表；
- 平台相关假设与证据缺口；
- 适用性判定（适合/不适合/信息不足）；
- 已有项目候选和排除原因；
- 保护目标 manifest；
- PoC 测试计划与退出条件；
- 保护前后语义验证计划；
- 残余风险与对外声明用语。

禁止输出：

- 未经授权的目标分析或第三方许可证绕过方案；
- 把未经验证的 anti-debug 细节列为默认安全措施；
- 将模型猜测写成真实的源码/运行时结论；
- 在没有用户批准时生成直接执行的命令或改写项目。

## 6. 建议测试套件

1. **结构保留测试**：源代码有结构性线索但没有明文秘密；检测器应报告结构暴露而不臆测业务语义。
2. **词法泄露测试**：发布工件含专用 canary 字符串；扫描应找到并定位。
3. **插桩失败测试**：删除/重命名预期 hook；构建应失败而非默默跳过。
4. **语义偏差测试**：注入一个故意错误的翻译或虚拟化 fixture；差分验证必须失败。
5. **运行时残留测试**：向测试日志/临时文件/core dump fixture 写入 canary；报告应检测到并指出范围。
6. **兼容性测试**：有反射、动态加载、异常和非 ASCII 文本的 fixture 必须正常运行，或清楚地标注不支持。
7. **来源/许可测试**：未知 LICENSE 的候选即使功能分数高，也必须被生产门控排除。
8. **取消与恢复测试**：取消构建后临时进程和工作区得到受控清理，原工作树不变。

## 7. 发布规范

- `lang-vmp-guide` 原包应以单独参考文件保存，文件名中保留 `original`。
- 不把原始 Skill 的内部代码/实现细节逐段复制到 PEA 的公开总结里；公开内容聚焦抽象方法论、验证方法与局限。
- 在维护者确认许可证前，README 必须注明原包是用户提供的研究参考，原包许可未在 ZIP 内核实；用户公开自己的 Skill 时可单独提交许可文件。
- PEA 任何生成的防护强度声明都必须附上测试环境、样本、工具版本、方法与限制。
